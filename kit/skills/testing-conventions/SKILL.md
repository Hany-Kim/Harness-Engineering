# 테스트 컨벤션

표본: `docs/exemplar/`의 테스트 파일을 먼저 읽고 같은 구조로 작성한다.

## 무엇을 테스트하나 (작업 유형별 의무)

- **새 기능**: happy path + 경계/실패 경로 최소 1개.
- **버그 수정**: 수정 전에 실패하는 재현 테스트를 먼저 작성하고, 수정 후 통과를 확인.
- **리팩터링**: 기존 테스트 그린 유지. 커버리지가 없으면 characterization 테스트를
  먼저 추가한 뒤 리팩터링한다.

## 구조와 네이밍

- given / when / then 3단 구조(주석 또는 블록으로 구분).
- 테스트 이름은 행동을 서술한다: `주문금액이_0이면_예외가_발생한다`,
  `returns 404 when note is missing`. `test1`, `shouldWork` 금지.
- 하나의 테스트는 하나의 행동만 검증한다.

## 목킹 경계

- 외부 시스템(HTTP API, 메일, 결제, 메시지 큐)은 항상 목킹한다.
- Repository는 서비스 **단위** 테스트에서 목킹 허용. **통합** 테스트는 실제
  DB(Testcontainers 등)로 — 인메모리 DB로 운영 동작을 가장하지 않는다.
- 서비스를 테스트하면서 그 서비스 내부 로직을 목킹하지 않는다.

## 완료 기준

- `harness/gates/gate.sh`의 test 단계 통과.
- 실패 경로 테스트 최소 1개 포함.
- 테스트가 없으면 그 기능은 미완성이다(골든 원칙 6) — 커밋 게이트 이전에 스스로 확인.
