# DB 마이그레이션 컨벤션

## 원칙

- **forward-only**: 적용된 마이그레이션은 절대 수정하지 않는다 — 되돌릴 일이 있으면
  보상 마이그레이션을 새로 추가한다(체크섬/이력 불일치 방지).
- 마이그레이션은 사람 리뷰 후에만 운영에 반영된다. 에이전트가 직접 운영 DB에
  적용하지 않는다.
- 파괴적 변경(DROP, TRUNCATE, WHERE 없는 UPDATE/DELETE)은 실행 전 반드시 사람 승인.

## 네이밍 — 생성 시점 타임스탬프로 고정

- Flyway: `V{yyyyMMddHHmmss}__{why_snake_case}.sql` — 버전과 설명 사이는
  **더블 언더스코어**. 버전은 파일을 만든 시점의 타임스탬프로 고정한다 —
  브랜치 간 번호 충돌이 원천적으로 없다.
  예: `V20260706143000__add_user_email_index.sql`
- Alembic: revision message에 WHY를 snake_case로. autogenerate 결과는 반드시
  손으로 검토한다(의도치 않은 drop 포함 여부).

## Flyway out-of-order 정책 — 운영 순차, 로컬 유연

- **운영/공유 환경은 순차 적용이다** (`outOfOrder=false` — Flyway 기본값).
  out-of-order를 켜는 설정을 저장소에 커밋하지 않는 것으로 기본값이 강제된다 —
  순서가 어긋난 마이그레이션은 배포/validate 실패로 드러나야 한다.
  코드로 못박고 싶으면 운영 프로파일에 `out-of-order: false`를 명시한다
  (설정 예시: docs/architecture/stack.md).
- **로컬만 유연 허용**: 브랜치 병행 개발 편의로 `outOfOrder=true`를 쓰되,
  **커밋하지 않는 로컬 프로파일에서만** (예: gitignored `application-local.yaml`).
- **순서 의존 마이그레이션을 만들지 않는다**: 다른 브랜치의 미머지 마이그레이션이
  먼저 적용됐다고 가정하는 SQL 금지. 로컬 out-of-order는 적용 "순서"의 동일
  재현을 보장하지 않는다 — 순서 독립이 이 정책의 전제다.
- **머지 전 재넘버링으로 단조성 유지**: 내 마이그레이션 타임스탬프가 base 브랜치의
  최신 버전보다 과거라면, **공유/운영 환경에 아직 적용되지 않은 파일에 한해**
  타임스탬프를 현재로 재발급한다. 공유 환경에 이미 적용된 파일은 절대
  재넘버링하지 않는다(forward-only와 같은 이유).

## 체크리스트 (완료 기준)

- [ ] 스키마 변경과 코드 변경이 같은 계획(docs/plans/)에 묶여 있다.
- [ ] 롤백 전략이 계획 §6에 있다(보상 마이그레이션 초안 포함).
- [ ] 대량 데이터 변경이면 배치/락 영향과 실행 시간 추정을 계획에 명시했다.
- [ ] 로컬/테스트 DB에서 적용·재적용을 확인했다.
- [ ] 순서 의존이 없다. 머지 직전 base의 최신 버전보다 내 타임스탬프가 새롭다
      (아니면 재넘버링했다).
