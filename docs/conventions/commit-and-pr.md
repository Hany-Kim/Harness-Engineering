# 커밋 / PR 컨벤션

## 커밋

- Conventional Commits: `<type>(scope?): 요약` — type ∈
  feat | fix | refactor | test | docs | chore | perf. 요약은 한국어.
- 커밋 하나 = 관심사 하나. 계획 문서의 Step 단위로 나눈다.
- 본문에는 WHY(무엇은 diff가 말해준다). 관련 계획/티켓을 언급한다.
- 게이트 우회 금지: `--no-verify`, `--no-gpg-sign`을 절대 쓰지 않는다. 게이트가
  실패하면 원인을 고친다 — 검사를 끄지 않는다.
- commit / push는 명시 요청·승인 하에서만. push는 작업 브랜치만.
- 티켓 업데이트는 커밋마다 하지 않는다 — PR 시점에 1회로 모아서 한다(아래).

## PR / MR

- 제목은 커밋 규칙과 동일. 본문에 반드시 포함:
  1. 계획 문서 링크(`docs/plans/<slug>.md`)와 티켓 키
  2. 변경 요약(파일이 아니라 행동 기준)
  3. `/verify` 결과 증거(실행한 명령 + 결과)
  4. 주의할 점(마이그레이션, 설정 변경, 롤백 방법)
- 머지 전 승인자가 누구인지 사람에게 확인한다. 셀프 머지 금지.
- 머지 후 계획 frontmatter가 `verified`인지 확인하고 작업을 종료한다.

## PR 시점 Jira 티켓 검토·업데이트

PR을 열 때(작업 단위가 리뷰로 넘어가는 시점) **1회** 수행한다 — 커밋마다 갱신하지
않는다. 연결된 티켓(`JIRA_PROJECT_KEY` 기반)의 기존 내용을 먼저 **검토**하고 작업
내용을 **업데이트**한다. 접근은 Atlassian MCP 경유(integrations 규약 참조) — 티켓
코멘트·상태 전이는 외부 상태 변경이므로 **사람 승인 하에만**, secret/개인정보는
마스킹한다.

작성 원칙 — **비개발자도 읽는다는 전제로**:

- **목적·의도를 먼저.** "무엇을 왜 했는가"를 업무 언어로. 코드가 아니라 배경부터.
- **효과를 한 줄.** 사용자·운영 관점에서 무엇이 달라지는지.
- **핵심 기술만 필요한 만큼.** 중요한 기술 결정(예: 인증 방식 변경, 캐시 도입)은
  언급하되 라이브러리·클래스·파일명 나열은 금지 — 가독성이 우선이다.
- 기존 티켓 설명과 **모순되면 덮지 말고** 무엇이 바뀌었는지 함께 남긴다.

업데이트 템플릿:

```
[무엇을/왜]  <업무 언어 한두 문장 — 배경과 목적>
[효과]       <사용자·운영 관점의 변화 한 줄>
[참고]       <중요한 기술 결정 1~2개만, 선택>
[링크]       <PR>
```

예: "로그인 실패 시 안내가 없어 이탈이 잦던 문제를 해결. 실패 사유별 메시지를
보여주도록 함. / 효과: 사용자가 원인을 알고 재시도 가능. / 참고: 인증 오류 코드
표준화." — 프레임워크·함수명은 넣지 않는다.
